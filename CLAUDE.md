You will be writing VHDL. 

Some best practices:
1. Functions are really bad, don't use them. Ever. Instead, create the primitive devices (if they don't already exist) to create that thing, and build off the primitives. Example: Barrel Shifters. Never use a function, just create generic registers and generic muxes. Example: SRT Division. The predictive tables are similar to regular lookup tables, so just use that.
2. Generics, as much as possible. Use them everywhere. Primitives keep your code clean and traceable.
3. For anything with a non-power-of-two width (mux N inputs, leading-zero count, etc.), build a recursive core that only handles powers of two, then wrap it: pad up to the next power of two and instantiate the core. `generic_mux`/`generic_mux_core` and `generic_lzc`/`generic_lzc_core` are the reference examples. Don't hand-roll a width-N version separately from the width-2^N version.
4. Never trust a combinational full/empty/status flag derived from a *speculative next-state* signal (e.g. "what the pointer would be after this write") if that same flag also gates whether that next-state transition happens — that's a combinational loop. Derive the flag from the *registered* (last-cycle) state instead. `generic_async_fifo.vhdl`'s header comment has the worked example: an early version compared `wfull` against `wptr_gray_next` and looped; the fix compares against the registered `wptr_gray`, which also happens to get the fill boundary right (accepts the write that completes the FIFO to exactly `DEPTH`, blocks the one after).
5. Document non-obvious protocol/reset conventions directly in the entity's header comment, not just in commit messages or here — e.g. `generic_rr_arb.vhdl` explains why `last_grant` resetting to 0 makes the first post-reset grant come out as requester 1, not 0.
6. Every primitive gets a self-checking testbench in `test/`, named `tb_<entity>.vhdl`, checked into the repo (not left in a scratch/build directory). Run the whole suite with `test/run_tests.sh` before calling anything done — it compiles and runs every testbench from a clean GHDL build and fails loudly (nonzero exit) on any that don't report "ALL PASS". Exhaustively check small/structural primitives (every input pattern, not a handful of hand-picked cases) where that's feasible — `test/tb_generic_lzc.vhdl` sweeps every value for two widths and is what caught the padding bug in practice #3 above.
7. In a testbench, `wait until rising_edge(clk)` returns at the clock edge itself, before any downstream combinational logic has settled through its delta cycles — checking a DUT output (a flag, a mux'd value, anything not a bare register) right after that wait without an additional `wait for 1 ns;` will read a stale value and produce a false failure. This bit twice while building `generic_async_fifo`'s testbench.
8. When testing a dual-clock/CDC design with "the same period on both sides" as an isolation case, generate the two clocks independently (two separate `<sig> <= not <sig> after T`), never derive one from the other (`rclk <= wclk`) — a continuous assignment like that adds a one-delta-cycle lag on the derived clock, which races against anything in the testbench timed off the source clock and produces failures that look like DUT bugs but aren't. Cost real debugging time on `generic_async_fifo`'s testbench before the fix was to generate `rclk` independently.
9. If you can't find the bug by re-deriving the waveform by hand, add real instrumentation (a monitor process on the DUT's own internal signals via VHDL-2008 external names, `<<signal .tb.dut.sig : type>>`, or temporary `report` lines in the DUT itself) rather than guessing again — this is how every real bug in this session got found (async FIFO's combinational loop, its full/empty boundary, and the two testbench-timing bugs above). External names as an *architecture-declarative-region alias* pointing into a same-testbench DUT instance failed to elaborate on GHDL here ("component instance ... is not yet elaborated") even though the path was correct; the reliable fallback was adding temporary debug output ports to a scratch copy of the DUT (never committed) and wiring them to plain signals instead — slower to set up, but it works.
10. A flag meant to mean "the data is ready" must be derived with the *same* latency as the data it describes, not just look similarly registered. `sys_array.vhdl`'s `first_out`/`last_out` vs `p_out` is the worked example: both seemed like "one register hop" from the same source (`act_skew`'s output), but `p_out` has a hidden extra hop — `dsp_mac2`'s weight-swap-then-multiply pipeline means the cycle `first` loads a new weight pair is *not* the cycle that weight first appears in `p_out` (`dsp_mac2.vhdl` S2.1's item 1 vs item 3, both non-blocking off the same edge) — while the flag chain (`pe_cell`'s `fl_reg`) has no such dependency and reads "ready" a cycle early. Found by probing `pe_column`'s row-15 internals directly (practice #9), not by re-deriving the 16-deep pipeline by hand a third time after two attempts disagreed with simulation. Fixed by adding a uniform +1 to `ctrl_skew`'s stage list in `sys_array.vhdl` rather than changing `pe_cell` itself, since `first_out`/`last_out` also drive the next column's horizontal wavefront trigger and delaying *that* would break the weight-swap timing the whole scheme depends on — when two consumers of the same signal need different timing, fix it in the one consumer-specific path, not the shared source.
11. Two peer registers on the *identical* clock edge, connected only by a combinational path (a mux, an adder, anything with zero registers of its own), cannot exchange a "new value" on that same edge — the downstream register always samples the upstream one's *pre*-edge value, standard delta-cycle semantics, not a bug, but easy to get backwards when designing a same-cycle handshake. `weight_loader.vhdl`'s original design pulsed a `first_out` flag on the identical cycle as `swap`, reasoning "the mux already switched, so the flag can fire now" — but `dsp_mac2`'s own weight register is a *separate* peer register on that same edge, so it always latched the *outgoing* tile's weight, not the incoming one. A testbench that only checks `weight_loader`'s own outputs in isolation (`tb_weight_loader.vhdl`, sampling well after the edge, by which point everything has settled) cannot catch this — it takes an integration testbench that wires the same-cycle signal into the *actual downstream register* (an uncommitted scratch testbench, then `tb_array_seq.vhdl` for real) to see it. Fixed by moving the one-cycle stagger into the state machine that already has to exist for another reason (`array_seq`'s own tile-transition logic), rather than adding a delay register to the peer entity — see `array_seq.vhdl`'s header.
12. A GLOBAL, undelayed bus read by N consumers that each latch it at a *different*, data-dependent cycle (because they're chained through their own registers first) must stay stable for the *slowest* consumer's full latency, not the fastest one's. `sys_array.vhdl`'s `SYSTOLIC` mode chains column `c`'s inputs from column `c-1`'s own registered output, so column `c`'s row `r` latches `first` one full cycle later per column hop — but `weight_loader`'s `w1_next`/`w2_next` bus is one global signal every column reads identically, with no matching per-column delay. `08-vhdl-implementation-spec.md` S3.3's literal "direct-write needs only `B >= R = 16`" is true only for a single column (or `TREE` mode, where every column gets the same broadcast) — under `SYSTOLIC` with `DSP_COLUMNS > 1` the real minimum is `B >= ROWS + DSP_COLUMNS` (`array_seq.vhdl`'s `MIN_TILE_AGENTS`, caller-computed, not a bare default), or the far columns silently read an already-swapped-away tile's weight. Found by an integration test (`tb_array_seq.vhdl`) showing a column-index-dependent pattern of wrong sums at `B=16` that vanished at the wider spacing — a case where the module list's own stated number needed correcting for this repo's specific implementation, not silently accepted.
13. Dropping a pipeline's enable (`ce`) the instant the *last* input has been presented, without waiting for it to finish draining through however many registered stages still hold it in flight, freezes those stages mid-drain rather than flushing them — a `generic_delay_line`-style stage only advances on `ce`, so whatever value is sitting in it when `ce` drops just sits there, looking like a "stuck" or duplicated output to anything watching downstream. `array_seq.vhdl`'s first draft went straight from its last active cycle to idle on `finishing`; the fix is an explicit `DRAIN` state that holds `ce` high (with no new agents being presented) for the same latency computed for practice #12 above, before `done` actually pulses. Both this and practice #12 were found by the *same* testbench run (`tb_array_seq.vhdl`) — a lesson to build the integration test before assuming a sequencer's "stop" logic is as simple as "stop advancing."
14. Don't assume a quantity described only as "the scale" is non-negative just because every format you'd checked so far happened to be. `int_mul_scale.vhdl`'s first version typed `group_scale` as `unsigned` with the explicit (and, for Q3_K/Q4_K, correct) reasoning "it's a magnitude, never a signed delta" — but `08-vhdl-implementation-spec.md` S2.1's own table calls Q6_K's group scale out as explicitly "8-bit signed" (matching ggml's `block_q6_K`, whose `scales` field is a plain `int8_t` array, unlike Q3_K/Q4_K's packed-unsigned encoding). Found while deriving `q6k_unpack.vhdl`'s scale output and checking it against an already-built, already-tested consumer's port type — not something either entity's own testbench alone would have caught, since `int_mul_scale`'s exhaustive sweep never had a reason to try a negative scale, and `q6k_unpack` has no consumer to type-check against until you go looking for one. Fixed by widening `group_scale` to `signed` (strictly more general: a non-negative value reads the same as signed or unsigned, so Q3_K/Q4_K's behavior is unchanged). When building a new format's decoder against an existing, older consumer, checking that consumer's *documented assumptions* — not just its port widths — against the new format's own spec text is worth doing before wiring them together.
15. When a project-specific packing choice (a per-weight constant offset, chosen so a value fits a signed hardware slot) doesn't match the *format's own* native representation, the compensation needed to recover the true value can be a term nobody has written down yet — and that gap can sit one level removed from where you're looking. Q4_K's true ggml formula is `d·sc·q − dmin·m` using the raw *unsigned* nibble `q` directly (no per-weight centering — Q4_K's asymmetry is handled entirely by the per-group `m` term). This project's array packs Q4_K's weight as `q−8` instead, matching Q3_K's/Q6_K's own per-format offset convention (which, for THOSE two formats, IS ggml's native formula, so no compensation is needed there) — but for Q4_K this introduces a `Σ(sc·(q−8)·x) = Σ(sc·q·x) − 8·sc·Σx` discrepancy that needs an additional `+8·d·sc·Σx` term on top of the already-documented `dmin·m·Σx` subtraction (`int_acc.vhdl`'s `min_term`), and neither `08-vhdl-implementation-spec.md` S2.2's rescaler-ops table nor `int_acc.vhdl`'s header mentions it. Found while writing `q4k_unpack.vhdl`'s header and re-deriving the array's actual arithmetic against ggml's true formula, not by testing (there's no rescaler built yet to test this against) — flagged there rather than silently built around, since resolving it means either adding that term to whichever entity ends up computing Q4_K's final rescale (`group_scale_acc`/`sb_finish`, not yet built) or confirming, with a real derivation, that it isn't actually needed.
17. When testing an entity that CONSUMES an approximation-based primitive (a lookup table, an interpolator — anything whose own accuracy already has its own dedicated testbench), don't re-test that primitive's accuracy by tolerance-checking the consumer too — configure a deliberately DEGENERATE table instead (every entry the same value, slope=0) so the primitive's output collapses to one small, hand-computable function of its input, and the consumer's own wiring/sequencing can be checked bit-exactly. `tb_act_quantizer.vhdl` needed two chained `recip` calls (`generic_lookup.vhdl` TAB_MANT) to get both `act_quantizer.vhdl`'s per-element multiplier and its stored `scale` output; with a real reciprocal table, only the FIRST call (on a power-of-two input) would land on an exact table point — the SECOND call (on the first call's result, generally not a power of two) would need genuine interpolation, forcing a tolerance-based check. Loading `{value=1.0, slope=0}` into every table entry instead makes `generic_lookup` return `2**-(unbiased_exponent)` for ANY input regardless of mantissa (since `local_mul(0, frac) = 0` zeroes out the interpolation term unconditionally) — not the true reciprocal in general, but an exact, always-hand-computable one, since `tb_generic_lookup.vhdl` already separately covers whether the REAL tables are accurate. Use a real (accurate) table only when the accuracy of the interpolation itself is what's under test.
18. **Practice #15's gap is now RESOLVED, not just flagged** — `group_scale_acc.vhdl` implements the `+8·d·sc·Σx` add-back, reusing the exact same multiplier shape the spec already calls for (`min_term`'s `m·Σx`), just added instead of subtracted and pre-shifted by `log2(WEIGHT_OFFSET)` (a free wire shift, `WEIGHT_OFFSET=8` being a power of two) — see that entity's header for the full re-derivation and `tb_rescaler_q4k.vhdl` for an end-to-end proof against a hand-computed true-ggml-formula example. Building it surfaced a NEW instance of the same bug class as practices #10/#11/#12, the first time `int_mul_scale.vhdl` and `int_acc.vhdl` were chained together: `int_mul_scale` registers its product on `ce` (1-cycle latency), and `int_acc` accumulates whatever its own `d` input reads *at the time of its own `ce` pulse* — feeding both primitives the identical raw `ce` train makes `int_acc` sample `int_mul_scale`'s *pre-edge* (previous group's, or garbage on the first pulse) product every time, the textbook same-edge peer-register race, just between two different primitives instead of within one entity's own draft. Fixed by registering `ce` through one extra `generic_register` stage (the same `ce_d`/`lane0_valid` pattern `dsp_mac2.vhdl` already uses) before it reaches `int_acc` — `rst` needs no such delay, since it clears `int_acc`'s own register directly and never passes through `int_mul_scale`. `sb_finish.vhdl`'s 12-step fp32 sequencer has the mirror-image lesson: two of its ten intermediate values (`min_contrib`, `delta`) are consumed the very next step after `generic_fpu` produces them, with zero slack — for those, a `generic_register` latch would add a full extra cycle too many, so the sequencer reads `generic_fpu`'s own output (`fpu_y`) directly instead of through a named register, while every other intermediate (consumed 2+ steps after production) does go through its own register. **The general rule: before chaining two already-registered primitives (or a state machine's own steps) together, count the exact cycle gap between when the producer's output becomes valid and when the consumer needs it — zero gap needs a direct/combinational read, a one-cycle gap needs exactly one extra register stage.** Getting this arithmetic wrong is easy even when you know the rule: this session's own `tb_group_scale_acc.vhdl` first draft asserted the wrong cycle for when a continuously-pulsed `ce` train's last group lands (assumed one extra drain cycle too many), because holding `ce` high across N groups back-to-back makes the two internal register stages overlap/pipeline rather than serialize — the fix was working out the actual overlapped timing on paper against the simulation's own waveform, not adjusting the DUT.

19. A "this phase is done" flag that's derived PURELY from the current state's own qualifying sub-conditions (e.g. `mode = MODE_K and step_last and q_idx_last`) is combinationally true only during the cycle immediately BEFORE the same edge that moves the state machine away from that qualifying state — and is therefore invisible to any synchronous consumer that samples it the normal way (`wait until rising_edge(clk); wait for 1 ns; check`, the exact idiom practice #7 already established, used by every testbench and by any real downstream sequencer polling a `done` port): by the time that check runs, the state has already moved on and the combinational condition has already gone false again. `softmax_online.vhdl`'s first draft built `k_done`/`v_done` this way and its own testbench hung forever (`wait_pulse` never saw `done='1'`) — found by adding a cycle-by-cycle debug trace (practice #9) and hand-counting exactly which edge the combinational condition was true during vs. which edge a post-edge check would land on. **The fix, and the general rule going forward: a `done`-style output meant for an external/synchronous consumer needs either a genuinely dedicated one-full-cycle terminal state (`act_quantizer.vhdl`'s `PH_DONE`, `kv_reader.vhdl`'s `PH_DONE`, `attn_finish.vhdl`'s `PH_DONE` — all already correct, unaffected) or, when the state machine doesn't have (and doesn't otherwise need) a dedicated terminal state, an explicit one-cycle register on the combinational "about to be done" condition** (`softmax_online.vhdl`'s `k_done_reg`/`v_done_reg`, `pv_lanes.vhdl`'s `chunk_done_reg`, built correctly from the start there once this pattern was known) — either way, the flag must still be asserted for a full clock period that starts AFTER the transition, not one that ends AT it. A flag built from an AND with an ALREADY-correctly-built flag of this kind (e.g. `attn_seq.vhdl`'s `out_valid <= state = S_QUERY_WAIT and af_done`) does NOT need its own extra register — `af_done` is already stable for a full cycle and `attn_seq`'s own `state` doesn't change on that same edge, so their AND inherits the same one-full-cycle stability; the risk is specifically in flags built entirely from signals that ALL change together at the disqualifying edge.
20. A register whose ONLY clear/reset path is a pulse generated by its own downstream consumer — fired only AFTER that consumer has already processed at least one full cycle of real accumulated data — starts simulation life uninitialized (`'U'`) and can stay permanently poisoned, since `std_logic` arithmetic propagates `X`/`U` (`'X' + anything = 'X'`) and nothing else ever forces a clean `0` in. `pv_lanes.vhdl`'s per-lane `int_acc` instances were wired with `rst => acc_rst_lane`, a pulse the FOLD sequencer itself generates only once it has already read that lane once (clearing it for the FOLLOWING chunk) — so the very first chunk's accumulate wrote real terms on top of an undefined base, and the first fold's `CVT_I2F` read garbage every time, one full chunk before the lane's own rst pulse ever fired. Found via `tb_pv_lanes.vhdl` reading back `0x00000000` for every lane on chunk 1 (not garbage — the garbage happened to net out to a clean-looking zero through `generic_fpu`'s own unpack/pack logic, which made it LOOK like a "write never happened" bug at first rather than a "read garbage" one) and confirmed by a falling-edge-sampled debug trace (mid-rising-edge combinational sampling gave misleading transient values here — see the note added to practice #9's own toolbox: prefer sampling on `falling_edge(clk)` over an event-triggered `process(sig)` monitor when a signal depends on a multi-stage combinational chain, since the event-triggered version can catch same-timestamp transients before they finish settling). **Fixed by OR-ing the chip-wide `rst` into the per-lane clear** (`acc_rst_lane <= '1' when rst = '1' else acc_rst_pulse when ... else '0'`) so the accumulator has a clean, defined value before its first-ever use regardless of whether its own natural clear condition has ever fired yet — worth checking for on any other register whose only enumerated clear condition is downstream-generated rather than tied to chip reset or a caller-driven "start of a fresh run" pulse.

## Folder structure

`src/primitives/` is for generic, reusable L0/L1 building blocks only (registers, muxes, arithmetic — anything usable from more than one architectural unit). Everything L2 and above lives in its own `src/<unit>/` directory, one per named unit from `syseng_docs/03-architecture-units.md`/`04-vhdl-module-list.md`, not lumped into `primitives/`: `src/array/` (U9, matrix array — `pe_cell`/`pe_column` so far), `src/weight/` (U7, weight path), `src/rescaling/` (U10), `src/activation/` (U8), `src/attention/` (U11), `src/vector/` (U12's `vec_seq`/`topk_sampler` — NOT `generic_vector_unit`, which is the reusable per-lane primitive and stays in `primitives/`), `src/memory/` (L3), `src/control/` (L4), `src/tile/` (L5). These directories exist (empty, scaffolded) even before there's code to put in them — check for the matching one before creating a new file rather than defaulting to `primitives/` or inventing a different name.

Also now built, under `src/array/` — all of **L2's matrix array (U9)**, including `array_seq`: `pe_cell` (one `dsp_mac2` plus registered `x`/`first`/`last` pass-through, "behav"/"xilinx" selected by which architecture you bind to, matching `dsp_mac2`'s own convention rather than an `ARCH` generic — `08`'s literal generic list for `pe_cell` has no `ARCH`); `pe_column` (16 `pe_cell` chained vertically through the `p_in`/`p_out` dot-product cascade, row 0's `p_in` tied to 0 internally); `act_skew` (the one-time, per-tile input skew bank — 960 FFs = (0+1+...+15) × 8-bit width, matching `04`'s own figure — that turns a simultaneous 16-wide activation vector into the per-row-staggered form `pe_column`'s cascade needs) and `ctrl_skew` (a generic per-channel flag-delay bank, reused for both its own output-side-skew job and `sys_array`'s flag/data-alignment fix below); `sys_array` (`DSP_COLUMNS` `pe_column`s wired either `ACT_DIST=SYSTOLIC` — chained column to column, `c` clocks of natural stagger — or `TREE` — broadcast after a fixed `TREE_DEPTH`, built both ways per `08`'s "build both, decide by synthesis"; weight bus is direct-write only, `[D]`, since `dsp_mac2` has no cascade port for chain-load); `weight_loader` (direct-write's other half — a minimal ping-pong register bank, `swap` in/`w1_next`+`w2_next` out, nothing else — see below for why it lost the `first_out`/`last_out`/`is_last` ports an earlier draft gave it); and `array_seq` (the control sequencer — two counters, `tile_cnt`/`agent_cnt`, drive `weight_loader.swap` and `sys_array.ce`/`first_in`/`last_in`; a `weight_ready` handshake `[D]`, not in the spec text, stalls at a tile boundary rather than silently swapping in a half-loaded buffer).

`pe_column.vhdl`'s header documents the dataflow model all of this was built against, worked out from `08`/`04`'s prose since the array's actual cycle-accurate reference (`ref/chain_sim.py`) isn't in this repo: activation flows **horizontally** (row r's `x_out` feeds row r's counterpart in the *next column*, not the next row) while the partial sum flows **vertically** — a classic weight-stationary systolic array — so `pe_cell`'s `x_in`/`x_out`/`first_in`/`first_out`/`last_in`/`last_out` are per-row and exposed by `pe_column` for `sys_array` to wire column-to-column, never chained within a column.

Four hard-won, easy-to-repeat bugs worth knowing before touching this code (all now in this file's numbered practices #10-#13): (1) `first_out`/`last_out` are **not** safe to treat as "data is ready" signals as-is — `dsp_mac2`'s weight-swap-then-multiply pipeline means `p_out` lands one cycle later than the flags that nominally describe it, fixed with a uniform +1 in `sys_array`'s `ctrl_skew` stage list, not in `pe_cell`; (2) a `weight_loader` draft used `active xor swap` to make its output mux reflect a same-cycle swap immediately, reasoning the registered `active` bit would still read its pre-edge value at that point — simulation showed that's backwards, so the fix was simpler than the original code: just use `active` directly; (3) a *later* `weight_loader` draft tried pulsing its own `first_out` on the identical cycle as `swap` — a same-clock-edge peer-register race with `dsp_mac2`'s weight register, caught only by an integration test, not by `weight_loader`'s own isolated testbench; the fix moved out of `weight_loader` entirely and into `array_seq`'s state machine, which needs the one-cycle stagger anyway; (4) `sys_array`'s `SYSTOLIC` mode chains columns through their own registers, so `08` S3.3's literal `B >= ROWS = 16` direct-write minimum is wrong for `DSP_COLUMNS > 1` — the real minimum is `B >= ROWS + DSP_COLUMNS`, and `array_seq` additionally needs an explicit post-run `DRAIN` state (holding `ce` high with no new agents) of the same length, or the last tile's results get stuck/duplicated at the array's output instead of cleanly flushed. `array_seq.vhdl`'s header has the full derivation for both.

`array_seq`'s own generics/ports and the full timing derivation are documented in `array_seq.vhdl`'s header — the short version: `start`/`num_tiles`/`tile_agents` load a run, `weight_ready` gates each swap, and `MIN_TILE_AGENTS` is a generic the *caller* must compute correctly for their own `DSP_COLUMNS`/`ACT_DIST` choice (the default of 16 only matches `DSP_COLUMNS=1`) — `tb_array_seq.vhdl` is the first (and so far only) testbench exercising array_seq+weight_loader+sys_array together, and is what caught bugs (3) and (4) above; nothing smaller could have.

Also now built, under `src/weight/` — all of **L2's weight path (U7)**: `wt_pack` (a small generic 2-lane packer mirroring `dsp_mac2`'s own `a_word` formula — its real consumer is undetermined, `[D]`, flagged rather than guessed, since `weight_loader` already takes separate per-lane buses and doesn't need a pre-packed word); `q3k_unpack`/`q4k_unpack`/`q6k_unpack` (one raw super-block in, 16 groups of 16 weights + per-group scale(s) + shared fp16 `d` out — **[R], best-recall reconstructions of ggml-quants.c's block layouts, a deliberate user-approved risk**: that source isn't in this repo, so every testbench for these three checks the VHDL against an *independently re-derived* Perl model (`test/gen/gen_q3k_vectors.pl`/`gen_q4k_vectors.pl`/`gen_q6k_vectors.pl` — Perl, not Python like the other `test/gen/` generators, since no Python interpreter was available when these were written), never against real ggml — treat the numeric output as unverified until checked against the real source or a numpy oracle, same status as `dsp_mac2`'s `xilinx` architecture); and `wt_reader` (a generic double-buffered byte-stream assembler — `[D]`, since no DDR4/DMA read-port convention exists anywhere else in this repo yet to match against; byte-at-a-time input, widening to match a real burst is future work once `dma_rd` exists). Two real findings surfaced while building these, now practices #14/#15: `int_mul_scale.vhdl` (already built, before this work) assumed an unsigned scale, but Q6_K's is genuinely signed — fixed, its interface is now `signed`; and Q4_K's `q−8` array-packing convention needs a compensation term in the rescaler that nothing in the spec documents — flagged in `q4k_unpack.vhdl`'s header at the time, since resolved (see practice #16 and the next paragraph).

Also now built, under `src/rescaling/` — all of **L2's rescaler (U10)**: `group_scale_acc` (per-column/per-lane scale-multiply-and-accumulate over 16 groups, `HAS_MIN_TERM` generic selecting Q4_K's extra path — this is where practice #15's gap actually gets resolved, with the `+8·d·sc·Σx` add-back reusing `int_mul_scale`'s own multiplier shape rather than a new primitive; see its header for the full derivation and practice #16 for the pipeline-stagger bug found while wiring `int_mul_scale`+`int_acc` together for the first time); `sb_finish` (a 12-step sequencer issuing `i2f`/`f16_to_f32`/`fp32_mul`/`fp32_add` through one shared `generic_fpu` instance to convert `group_scale_acc`'s two integer accumulators into a signed fp32 delta and read-modify-write it into an `acc_ram` slot, `first`-gated so a fresh output address starts from 0 instead of reading stale RAM); `acc_ram_bank` (a generate-loop bundle of `NUM_COLUMNS` independent `generic_sdp_ram` instances, one per column, flattened-bus ports matching this project's existing per-column convention rather than a VHDL array port type). Neither `group_scale_acc` nor `sb_finish` implements `04` S2.2's "shared/time-multiplexed across several columns" area optimization (`min_term`'s "0.5 per column", `fp32_mul`'s "8 shared per tile`) — both build one full, dedicated instance per column instead, `[D]`, correctness-first with the TDM resource-sharing left as a later synthesis-area pass. `tb_rescaler_q4k.vhdl` chains all three together (`group_scale_acc` → `sb_finish` → `generic_sdp_ram`) against a from-scratch hand-computed example proving the end-to-end result matches ggml's true `d·sc·q − dmin·m` formula despite the array only ever computing on the packed `q−8` weight — the concrete, checked closure of practice #15.

Also now built, under `src/activation/` — all of **L2's activation buffer and quantizer (U8)**: `act_quantizer` (per-256-element block: streaming abs-max through `generic_fpu`'s `ALU_MAX` — `abs(x)` is just clearing the fp32 sign bit, a wire op, not `int_absmax_tree`'s two's-complement trick, which only applies to integer magnitudes — then, since this design has no on-chip divider anywhere, `1/scale` via TWO chained `generic_lookup` TAB_MANT/`recip` calls rather than a hand-derived `1/127` constant: `inv_scale = recip(amax)*127.0`, `scale = recip(inv_scale)` `[[= amax/127 exactly, in real math]]`; then per-element multiply/round/clamp-to-±127 and the per-32 `Σq` group sums Q4_K's rescale needs — reusing `int_acc` for that last part, exactly the same accumulator `group_scale_acc` already uses for `Σx`, confirming `04`'s `act_quantizer`/`group_scale_acc` naming match isn't a coincidence) and `act_store` (double-buffered `act_ram`+`act_scale_ram`, ping-pong via the *exact* `weight_loader.vhdl` convention — `active` toggle, write-the-inactive-buffer, mux-the-active-buffer-for-read — right down to needing a real `rst` pulse before first use, since a bare `not active` toggle off an uninitialized register can never leave `'U'` on its own; caught by re-reading `weight_loader.vhdl`'s own header before writing this one, not by a failed simulation this time). Clamping to ±127 (not the full signed-8-bit range) is deliberate, not a rounding-scheme choice — `04`'s own note that activation value −128 breaks `dsp_mac2`'s packed-lane arithmetic at Q4_K's depth-32 spacing is why the quantizer, not the array, is where that gets enforced. `act_ram`/`act_scale_ram`'s real address space (`04`'s "36 agents × (4096+3584) elems") is deliberately NOT reconstructed — `act_store`'s `DEPTH`/`wr_addr`/`rd_addr` are plain caller-supplied generics/indices, `[D]`, same treatment as `wt_reader.vhdl`'s invented streaming interface, left for whichever control unit ends up owning the real layout. `tb_act_quantizer.vhdl` is also where practice #17's degenerate-mock-table testing technique was worked out, letting a lookup-table-consuming entity be checked bit-exactly instead of by tolerance.

Also now built, under `src/vector/` — **U12's `vec_seq`**, the descriptor-walking sequencer `lazuli.vhdl`'s own header explicitly says doesn't exist yet ("operand sequencing is the caller's job" — this entity is that caller). Resolves the "blocked on `ref/tpu.h`'s command struct" note the same way the weight path's own undetermined interfaces were resolved: rather than reconstructing an unverifiable raw 256-bit `tpu_cmd` bit-layout, `vec_seq` takes the descriptor already DECODED into typed ports (per-operand base address + 3 strides for source A/B/destination, `[D]`; shared loop trip counts `count0/1/2` across all three, `[D]` — a stride of 0 on any level lets that operand broadcast, e.g. a norm's gain vector, without needing independent counts per operand), `[D]`, matching `lazuli.vhdl` itself taking a typed `op`/`sub`/`cvt` rather than raw opcode bits — whatever eventually decodes a real `tpu_cmd` (`cmd_link`, not built) is the thing that should produce these fields. Walks the (up to) 3-level nested loop with a multiply-free "odometer" address stepper (checkpoint registers per loop level, same shape as `array_seq.vhdl`'s own counters) issuing ONE operand pair to a real `lazuli` instance at a time, waiting for it to retire before advancing — not pipelined across iterations, `[D]`, matching `08`'s own "latency matters more than throughput" characterization of this unit rather than being a shortcut. `tb_vec_seq.vhdl` is a real integration test (`vec_seq` driving an actual `lazuli` instance plus three `generic_sdp_ram`s standing in for operand/destination memory), not a synthetic port-level check, exercising both the plain-stride and the wrap-into-the-next-loop-level address-stepper paths.

Also now built, under `src/attention/` — all six entities of **L2's attention engine (U11)**: `qk_lanes` (NUM_Q parallel, purely combinational DIM-wide dot products — one `int_sum_tree` per resident query, reused as-is rather than a new reduction primitive, registered one cycle on `ce` — this is what actually spends GQA's "each K/V element reused by 4 query heads" reuse: one K read feeds NUM_Q dot products in parallel, not NUM_Q separate reads); `kv_reader` (walks a "4 KiB run" in K-then-V order, presenting one token at a time with a plain valid/ack handshake — `[D]`, the run itself is taken as ALREADY ASSEMBLED into an on-chip RAM, exactly `wt_reader.vhdl`'s own resolution for the same "no `kv_dma`/DDR convention exists yet" gap, and DIM=128/CHUNK=16/INT8 KV happens to reproduce `08`'s own "4 KiB" figure exactly, confirming INT8 KV is what its numbers were computed against); `softmax_online` (the online-softmax recurrence, per resident query, over ONE shared `generic_fpu`+`generic_lookup` pair, step-sequenced like `sb_finish.vhdl`/`act_quantizer.vhdl` — **[D] uses base-2 exponentials (`generic_lookup`'s native `TAB_FRAC`/exp2) instead of natural `e^x` throughout**, since softmax's normalized output is invariant to the exponential base used (`Softmax_b(x)_i = b^x_i / Sum_j(b^x_j)` for any consistent `b`), which avoids an extra fp32 multiply-by-`log2(e)` — and where practice #19's `k_done`/`v_done` registration bug was found and fixed); `pv_lanes` (DIM×NUM_Q parallel `int_acc` lanes for the always-live per-token P·V accumulate — no shared resource needed there, since `p` is a scalar per token and DIM is naturally parallel — plus one shared-`fpu` chunk-boundary fold sequencer that rescales-and-folds each lane's finished int accumulator into a persistent fp32 `o_acc`, where practice #20's uninitialized-`int_acc` bug was found and fixed); `attn_finish` (recip(l) via the SAME abs-max-free reciprocal trick `act_quantizer.vhdl` uses, then literally REUSES an internal `act_quantizer` instance wholesale for the "quantize back to int8" half, rather than re-deriving its ~250-line FSM, since `08`'s own "quantize back for the `o` matmul" is exactly that entity's job applied to attention's output instead of a generic activation block); and `attn_seq` (the top sequencer, array_seq.vhdl's role for this engine — **[D] control-ports-only**: every DATA bus between the other five entities, and kv_reader's own memory port, is wired DIRECTLY between them at the integration level, never relayed through `attn_seq`'s own ports, since `attn_seq` never needs to inspect or transform any of it, only sequence WHEN each producer/consumer acts — the one exception is `q_idx`, exposed so an external mux can select attn_finish's per-query `l_in`/`o_acc_in` slice out of `softmax_online`'s/`pv_lanes`'s NUM_Q-wide outputs). **[D] scope, one KV-head group per run**: same resolution as `vec_seq.vhdl`'s own "blocked on `ref/tpu.h`" gap — `attn_seq` loops chunks of ONE sequence for ONE resident KV-head group (its NUM_Q queries loaded into `qk_lanes.q_vec` and held stable by the caller, same CALLER CONTRACT as `vec_seq`'s `op`/`sub`/`cvt`) then NUM_Q `attn_finish` calls; looping over multiple KV heads or sequences (`08`'s "loops over heads... sequences") needs `kv_page_mgr`/`cmd_link` (L3/L4, not built) and is the caller's job for now, exactly like `vec_seq`'s own resolution. `tb_attn_seq.vhdl` is a real integration test (`attn_seq` driving actual instances of all five other entities plus a run-buffer RAM), proving the wiring end-to-end against a hand-derived example that deliberately exercises both a clean (power-of-two `l`, exact reciprocal) and an approximate (non-power-of-two `l`, including a downstream ±127 clamp) query in the same run.

**Not built — everything else in the spec:**
- **L2 — vector unit (U12), the rest of it:** `topk_sampler`.
- **L3 — memory system:** `ddr_arbiter`, `dma_rd`/`dma_wr`, `kv_page_mgr`, `kv_dma`. (The DDR4 controller itself is vendor IP, not something to write.)
- **L4 — control:** `cmd_link`, `csr_block`, `perf_counters`, `selftest`.
- **L5 — tile/chip:** `reduce_ring`, `tile_top`, `chip_top`.

Build order matters here: with the matrix array (U9), weight path (U7), rescaler (U10), activations (U8), the vector unit's `vec_seq` (U12), and now the whole attention engine (U11) all real, every L2 unit except `topk_sampler` is built — and three integration-wiring gaps are worth closing before starting new units, none with their own integration testbench yet: `group_scale_acc`/`sb_finish`'s `sum_x`/`act_scale` inputs finally have a real producer to wire to (`act_quantizer`'s `sum_out`/`scale_out`, with `act_store` sitting between them and the array); `vec_seq`'s `a_re`/`b_re`/`dst_we` memory ports need a real backing memory wired in place of `tb_vec_seq.vhdl`'s standalone `generic_sdp_ram`s (plausibly `act_store`'s own RAM, once its address space is resolved — see U8's own `[D]` note above); and `attn_seq`'s five sibling entities need a real backing memory wired to `kv_reader`'s run-buffer port in place of `tb_attn_seq.vhdl`'s standalone RAM, plus `qk_lanes.q_vec` needs a real source for the resident query vectors (both depend on `kv_page_mgr`/`kv_dma`, L3, not built, the same gap `kv_reader.vhdl`'s own header flags). After that, or alongside it: `topk_sampler` is the only remaining L2 work (independent of everything above). Control and tile/chip are last regardless — they wire together units that don't exist yet.
